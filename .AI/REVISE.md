아래 내용을 그대로 Claude Code에 붙여넣으면 돼. AGENTS.md 규칙에 맞춰 plan mode로 시작하고, 커밋을 작게 나누도록 구성했어. 같은 종류의 구멍이 다른 곳에도 있을 수 있어서 권한 점검도 같이 넣었어.

```markdown
# 보안 개선: 신원 바인딩과 권한 점검

## 배경
tlog_test 실제 API에서 다음을 재현했다.
1. 공격자가 피해자보다 먼저 피해자의 이메일로 가입한다.
2. owner가 그 이메일로 초대를 보낸다.
3. 공격자가 초대를 수락해 owner 또는 signer 권한을 얻는다.

이 서비스의 핵심은 "누가 승인했는가"다. 신원이 탈취되면 공격자가 자기 키를 등록해 책임자 이름으로 서명할 수 있으므로, 서명 검증이 모두 무의미해진다. 실제 사용자에게 공개하기 전에 반드시 해결한다.

장기 대책은 SPARCS SSO 도입이다. 이번 작업은 SSO 전에 취약점을 막고, SSO를 붙일 때 같은 문제가 다시 생기지 않게 구조를 잡는 것이다.

## 진행 방식
- plan mode로 시작한다. 아래 단계별로 변경 파일, 스키마 변경, 테스트 계획을 먼저 보여주고 승인받는다.
- 단계마다 커밋을 분리한다. 스키마 변경과 기능 구현도 분리한다.
- 각 단계가 끝나면 리뷰 가이드와 평가 기준 체크리스트 해당 항목을 적는다.
- 판단이 필요한 부분은 추측하지 말고 질문한다.

## 1단계: 재현 테스트 먼저 작성
- 위 공격 시나리오를 e2e 테스트로 작성한다. 현재 코드에서 실패(공격 성공)하는 것을 먼저 확인하고 보고한다.
- 이후 단계가 끝나면 이 테스트가 통과(공격 차단)해야 한다.

## 2단계: 초대를 토큰 기반으로 변경
- 초대 수락 조건을 "같은 이메일 계정인가"에서 "초대 토큰을 가졌는가"로 바꾼다.
- 토큰은 32바이트 이상 CSPRNG로 생성하고, DB에는 SHA-256 해시만 저장한다.
- 만료 시간(기본 72시간)을 두고, 수락하거나 거절하면 즉시 무효화한다.
- 초대 생성 응답에서 토큰을 포함한 초대 링크를 한 번만 반환한다. owner가 다른 채널로 직접 전달한다.
- 토큰 비교는 상수 시간 비교를 쓴다.
- 수락 시 초대 대상 이메일과 수락하는 계정의 이메일이 다르면 거부한다. (SSO 도입 후 이메일이 검증되면 이 검사가 의미를 갖는다.)
- 초대 취소 API가 없으면 추가한다(owner 전용).

## 3단계: owner 권한 부여 경로 제한
- 초대로 owner 역할을 줄 수 없게 한다. 초대 가능한 역할은 signer, issuer뿐이다.
- owner는 기관 생성자로 시작하고, 이후에는 기존 owner가 이미 멤버인 사용자의 역할을 바꾸는 방식으로만 부여한다.
- 마지막 owner는 제거하거나 강등할 수 없게 한다.
- 역할 변경은 audit_logs에 기록한다.

## 4단계: 키 승인 화면 보강
- owner가 키를 승인할 때 키 소유자의 가입 시각, 초대 생성 시각, 초대 수락 시각을 함께 보여준다.
- 초대 생성 시각보다 먼저 가입한 계정이면 경고 배지를 표시한다.
- 승인 버튼 옆에 "이 사람이 실제 본인인지 직접 확인했습니다" 확인 단계를 둔다.

## 5단계: 권한 전수 점검 (IDOR)
이번 취약점처럼 "누구의 요청인가"를 확인하지 않는 곳이 더 있는지 모든 Endpoint를 점검한다. 각 Endpoint마다 아래 표를 채워서 먼저 보고하고, 수정은 승인 후에 한다.

| Endpoint | 필요한 권한 | 현재 검사 | 문제 여부 |

특히 다음을 확인한다.
- 초대 수락·거절: 초대 대상 본인만 가능한가
- 키 승인·폐기: 같은 기관의 owner만 가능한가. 다른 기관의 키 id를 넣으면 막히는가
- 서명·거절: 요청에 지정된 signer 본인만 가능한가. 요청자 본인 서명이 막히는가
- 암호문 다운로드: 지정된 signer만 받을 수 있는가
- 문서 폐기: 같은 기관의 signer만 가능한가
- 멤버 역할 변경·제거: 다른 기관의 userId를 넣으면 막히는가
- 목록 조회 API가 다른 기관의 데이터를 노출하지 않는가

발견된 문제마다 권한 실패 케이스 테스트를 추가한다.

## 6단계: SSO 도입 시 지킬 원칙 (문서화만, 구현은 별도 작업)
AGENTS.md의 도메인 규칙에 "신원" 섹션을 추가한다.
- 사용자 식별은 SSO가 발급한 고유 ID로 한다. 이메일은 식별자로 쓰지 않는다.
- 이메일은 SSO가 검증해 넘겨준 값만 신뢰한다. 클라이언트가 보낸 이메일은 쓰지 않는다.
- 이메일이 같다는 이유만으로 기존 계정과 SSO 계정을 자동 연결하지 않는다.
- SSO 도입 후 비밀번호 가입은 제거하거나, 유지한다면 signer·owner 역할을 받을 수 없게 한다.
- users 테이블에 `sso_uid`(unique), `email_verified_at` 컬럼 추가를 계획에 포함한다.

## 완료 기준
- 1단계 재현 테스트가 통과한다(공격이 막힌다).
- 5단계 점검표가 모든 Endpoint에 대해 채워져 있고, 발견된 문제가 수정되었다.
- AGENTS.md에 신원 원칙이 추가되었다.
- 남은 위험(SSO 전까지 이메일 미검증 상태 등)을 정리해 보고한다.
```
