# PLAN.md

현재 상태와 다음 작업만 기록한다. 공통 규칙은 `AGENTS.md`, API·화면 계약은 `MVP.md`를 따른다. 완료된 작업의 상세 이력은 Git에서 확인한다.

## 작업 방식

- 일반 UI·CRUD(목록·상세·로그 탐색·검색/필터 등)는 자동 Accept한다. 변경 계획을 알리고 필요한 검증 후 별도 승인 질문 없이 기능별 커밋·다음 단계 진행한다. 상세 경계는 AGENTS.md의 자동 Accept 정책을 따른다.
- 인증·권한·세션·암호학·append-only/STH·스키마/보호 영역은 계획 승인과 사람 검토 후 커밋한다. 스키마와 기능 커밋은 분리한다. 테스트·점검은 별도 승인 없이 진행한다.
- 인증 후속 수정 4건은 병렬 구현·상호 검토·통합 검증을 마쳤고 사용자가 최종 승인했다.
- 커밋 전 스테이징 목록을 확인하고 자동 생성 파일을 알린다. Push는 사용자가 한다.
- SPARCS KWS 시험배포는 승인됐다. 브라우저 암호학·Merkle 보호 영역은 상세 계획 승인 후 수정한다.
- 새 의존성은 이유·대안을 설명하고 출시 2주 이상 지난 안정 버전으로 고정한다.

## 현재 인증 정책

- 이메일·비밀번호 로그인을 유지한다. 이메일 소유 확인은 실명·소속 증명과 구분한다.
- 메일 토큰은 32바이트 난수, 15분 만료, 용도별 한 번만 사용한다. DB에는 SHA-256 해시만 저장하고 메일 링크 fragment로 전달한다.
- 메일 소유자가 새 비밀번호를 설정하면 인증 시각·비밀번호·token_version 증가·모든 인증/복구 토큰 삭제를 원자적으로 처리한다. 자동 로그인하지 않는다.
- JWT와 세션 쿠키의 수명은 4시간이다. 자동 갱신 없이 로그아웃·비밀번호 변경·메일 인증/복구에서 기존 세션을 무효화한다.
- 미인증 계정은 기관 생성·기관 접근·초대 조회/응답·역할 행사를 할 수 없다. 초대 수락에는 인증된 대상 이메일과 비밀 초대 토큰이 모두 필요하다.
- 기존 데이터는 사용자 확인상 테스트용이다. 미인증 기존 멤버십 또는 pending/active 키가 있는 계정은 자동 복구를 거부한다. 기기 교체 시 새 공개키를 등록하고 기관 owner가 기존 키를 폐기한 뒤 새 키를 승인한다. 폐기된 키의 과거 로그는 검증할 수 있다.
- SMTP를 기본 구현했다. Nodemailer 10.3.1과 타입 8.0.2를 고정했다. 실제 발송 설정은 `apps/api/.env.example` 참고. 비밀값은 사용자가 설정한다.
- 가입과 메일 요청은 유효한 입력이면 계정 상태와 무관하게 같은 202 응답을 준다. SMTP 전송 실패 시 해당 토큰을 삭제하고 식별 정보 없는 오류를 기록한다. SMTP 호출 여부에 따라 응답 시간은 달라질 수 있다.
- 발표는 미리 준비한 데모 계정과 기관으로 문서 전달 → 책임자 서명 → 공개 검증을 시연한다. 메일 발송과 초대 절차는 발표의 선행 조건에서 제외한다. Students 등 실무 서비스와 연결할 때 SPARCS SSO와 초대 정책을 함께 검토한다.

### 최종 승인된 인증 변경

1. 미인증 계정의 인증·복구 시 새 이름과 비밀번호, 인증 시각, 세션 버전을 한 트랜잭션에서 갱신한다. 인증 완료 계정의 비밀번호 복구는 기존 이름을 유지한다.
2. 유효한 가입 요청은 `202 { accepted: true }`를 반환한다. 신규 계정에는 인증 메일, 기존 계정에는 상태에 맞는 가입 시도 안내와 복구 방법을 보낸다. 반복 가입 시 계정 정보와 사용 중인 복구 링크를 보존한다.
3. 웹은 `pnpm -F web start`로 실행한다. 직접 접속이면 소켓 IP를 쓰고, 앞단 프록시가 있으면 웹의 `TRUSTED_INGRESS_IP`에 실제 직전 프록시 주소 하나를 설정한다. 해당 프록시는 TCP 접속자의 주소로 `X-Forwarded-For`를 덮어쓰거나 그 주소를 마지막에 추가해야 한다. API의 `TRUSTED_WEB_PROXY_IP`에는 웹에서 들어오는 실제 소켓 주소를 지정한다. 설정을 비우면 API는 전달 헤더를 무시한다. API는 기본 루프백으로 바인드하며 분리 배치에서는 `API_BIND_HOST`와 내부 접근 경로를 정한다. 웹 빌드 시 `API_ORIGIN`은 해당 내부 API를 가리킨다.
4. 4시간 세션이 만료되면 작성 화면을 메모리에 보관하고 같은 페이지에서 재로그인한다. 계정·기관 권한을 다시 조회하고 같은 사용자의 허용된 입력만 복원한다. 보호된 웹 요청에서 작성 화면의 사용자 ID와 쿠키로 인증된 계정이 다르면 API가 412를 반환한다. 서명 화면의 파일·확인 상태 보존은 세션 D에서 연결한다.

재개 시 `.AI/AGENTS.md` → 이 문서 → `EMAIL_AUTH_REVIEW.md` → `AUTHORIZATION_REVIEW.md`를 읽는다. `REVISE.md`는 이전 요청 원문이며 최신 순서·정책은 이 문서를 따른다. Node는 현재 AGENTS와 package.json 모두 26/최소24.9로 일치하며 Node22라는 리뷰 지적은 현 파일과 다르다. 실제 newbie 서버 지원은 미확인이다.

### 세션 C: 로그·STH

- `log_state` 행의 `SELECT ... FOR UPDATE`로 append 직렬화. entry·leaf index·업무 상태·서명된 STH를 같은 트랜잭션에 저장한다.
- Ed25519 STH 비밀키는 `LOG_SIGNING_KEY`에서만 읽고 `packages/shared`의 canonical bytes에 서명한다. 임시 키로 서명 검증과 각 필드 변조·다른 공개키 거부를 확인했다.
- 운영자가 생성한 Ed25519 개인키를 PKCS#8 DER의 Base64 문자열로 주입한다. 세션 D에서 브라우저 검증을 연결할 때 대응하는 공개키를 웹 배포 설정에 고정한다.
- 첫 entry를 저장할 때 크기 1의 첫 STH를 발행한다. 그 전에는 `GET /log/sth`가 `204`로 응답하고 STH 이력은 빈 목록이다. consistency proof 범위는 `1 ≤ first ≤ second`다.
- 공개 API 5개에서 최신 STH, STH 이력, consistency proof, entry 목록, inclusion proof를 조회한다. 이력은 최신순 100건씩 `before`로 이어 읽고, entry는 `start`와 `end` 양 끝을 포함해 오름차순 최대 100건씩 읽는다.
- 임시 MySQL 8.0의 격리된 `tlog_test`에서 동시 append 20건의 연속 번호, 각 STH 서명, 20건의 포함 증명, 과거·최신 STH 간 일관성 증명 및 실패 시 업무 상태와 로그의 롤백을 확인했다. 빌드한 API로 실제 STH와 포함 증명을 조회했다. 전체 테스트 4,535개와 lint·API 타입 검사·API 빌드 통과.

### 세션 C: 멤버 키 API

- 본인 공개키 등록, 내 키 목록(owner는 기관 전체), 기관 멤버의 사용 가능한 키 조회, owner 승인·폐기를 구현했다. 서버는 공개키 원본 32바이트에서 SHA-256 지문을 계산한다. 서명 키 등록·사용은 인증된 signer에게, 암호화 키 등록은 인증된 멤버에게 허용한다.
- 등록 키는 pending이다. 같은 기관·사용자·용도에 active 키 하나를 허용한다. 승인과 폐기는 각각 `KEY_REGISTER`, `KEY_REVOKE`와 같은 트랜잭션으로 커밋한다. 목록의 승인·폐기 시각은 해당 로그에서 읽는다.
- 기관 행 잠금으로 멤버십·역할 변경과 직렬화하고 사용자 행 잠금 후 세션 버전을 재확인한다. 계정 복구로 무효화된 세션은 대기 중이던 키 등록도 완료할 수 없다.
- 암호화 키를 폐기하면 해당 기관·수신자의 pending 요청 중 그 지문으로 암호화한 파일이 남은 요청만 `needs_resend`로 바꾼다. 기관 owner는 종전 데이터의 미인증·역할 변경 멤버 키도 정리할 수 있다.
- 상호 검토를 마쳤고 전체 테스트 4,542개(실제 MySQL API e2e 178개 포함), lint, API 타입 검사·빌드가 통과했다. 빌드본에서 폐기된 키를 조회하고 해당 폐기 기록의 Merkle 포함 증명을 검증했다. 사용자가 멤버 키 API를 승인했다.

### 세션 C: 브라우저 키·관리 UI

- `apps/web/src/lib/crypto/keys.ts` 보호 영역 상세 계획 승인 후 구현한다. non-extractable Ed25519/X25519 키와 IndexedDB 보관.
- `/settings/keys`, 기관 키 승인·폐기 화면, 실제 브라우저 검증.
- 승인 화면에 가입·초대 생성·수락 시각, 초대 전 가입 경고, 직접 본인 확인 체크를 포함한다.

### 세션 D: 서명 흐름

1. **요청·파일:** 요청 생성, 암호문 업로드/다운로드, 내 요청 목록. 브라우저 HPKE Base mode 구조·AAD, S3 저장, 20MB 제한, `/orgs/[slug]/new`. 중복 발급 409와 거절 후 재요청 정책 확정.
2. **서명·거절:** `/inbox`, `/inbox/[requestId]`. 직접 복호화·해시 비교·책임 확인·서명. `ISSUE` append 후 ciphertext 삭제, 실패 시 재시도 대상으로 보존. 요청함 배지.
3. **문서·폐기:** 문서 목록/상세, 폐기 서명, `REVOKE` append. `/documents/[id]`.
4. **검증:** 해시 검색과 브라우저 서명·inclusion·consistency 검증, 결과 상태·알려진 한계 표시.
5. **로그 탐색기:** `/log`, STH 이력·entry 목록, `?first=&second=` consistency 검증.
6. **통합 e2e:** 요청→서명→inclusion proof→브라우저 검증. 다른 키·payload 변조·폐기 키·자기 서명·다른 기관 접근 거부.
7. **데모:** 기관 2·사용자 4·문서 8·대기 요청 2 시드, 시나리오 1~9. 최종 배포는 별도 승인 후 진행한다.

## 운영 전 확인과 미룰 항목

- KWS 웹 도메인의 HTTPS 인증서 검증은 통과했다. SMTP TLS와 실제 메일함 수신은 발송 설정 후 확인한다.
- 요청 제한은 API 프로세스별 메모리를 사용한다. KWS에서 웹과 API가 보는 실제 직전 프록시 주소를 확인하고, API를 여러 인스턴스로 운영할 때는 공유 카운터를 마련한다.
- 미인증 초대 메타데이터 노출은 API에서 차단했지만 이메일 탈취·실명/소속 확인까지 해결한 것은 아니다. 키 승인 시 직접 본인 확인을 유지한다.
- UI의 `tlog` 표기는 Witness로 바꿀 예정이다. 패키지명·JWT issuer/audience·암호화 프로토콜 문자열은 일괄 치환하지 않는다.
- 일정이 부족하면 `needs_resend` 재전송 UI → audit UI → 다국어 전환 → 모바일 세부 조정 → RFC 3161 TSA 순으로 후순위화한다.

## 실행 환경 메모

- Node 26(최소 24.9), pnpm 12, TypeScript 6.0. TS 7은 현재 도구 호환성 때문에 사용하지 않는다.
- MySQL `127.0.0.1:3307`, SeaweedFS S3 `8333`. 스토리지는 AWS SDK만 사용한다.
- Prisma 7.10.1 + MariaDB adapter. 생성 client는 Git에서 제외되며 build/dev/test가 생성한다. 기존 마이그레이션은 수정하지 않는다.
- 에이전트는 `.env*`를 읽거나 수정하지 않는다(`.env.example` 제외). JWT_SECRET은 최소 32바이트, LOG_SIGNING_KEY는 로그 단계에서 설정한다.
- `pnpm -F api test:e2e`는 `.env` 없이 별도 Prisma 설정으로 로컬 `tlog_test`에만 마이그레이션을 적용한다. DB reset·볼륨 삭제는 하지 않는다.
- NestJS Jest는 `--experimental-vm-modules`, Next는 `agentRules: false`. Next API 확인은 설치된 `apps/web/node_modules/next/dist/docs/` 우선.
- ESLint 10에 대한 일부 웹 플러그인의 peer 지원 범위 경고는 남지만 실제 lint는 통과한다.
- 파일 전달 필드는 `recipientFingerprint`, id는 UUIDv7, 시간은 UTC ISO 8601이다. 브라우저와 API를 실제로 연결해 개발하며 제품용 mock을 두지 않는다.
